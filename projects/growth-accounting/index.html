    Overlap Window：让 MAU 的每天变化都有用户可查

    移动支付 · Growth Accounting　SQL · 30 天滚动窗口 · 用户状态流转

    买量不断带来新客，月末 MAU 却几乎没涨。新增、留存、召回各有报表，但它们解释不了同一个问题：今天进入活跃池的人，有多少被退出的人抵消了？

    我以支付行为定义活跃，把相邻两天的 30 天用户集合对齐。两个窗口共享 29 天，只替换最早一天和最新一天：因此可以把净变化拆成新增、回流与退出，并从退出用户回查最后支付日和获客渠道。这里的精确性来自 Overlap Window 的边界。

    决策主线

    点第 02、03 步看窗口如何移动；第 05 步看 SQL，第 06 步看怎样接到渠道判断。

    ↓ 先用同一支付口径，把两天的用户集合对齐 ↓ 共享区间相同，集合差就能定位到边界 ↓ 边界解释清楚，再核对四种状态是否守恒 ↓ 恒等式对上，才值得把结果做成每天的表 ↓ 保留用户级流转，异常才能追到具体批次 ↓ 规模与质量分开后，再给预算复查排优先级
    窗口前进一步，变化只在两端。
    旧窗口 · 1/30
    1/1
    移出    1/2 — 1/30
    共享 29 天    1/31
    新窗口 · 1/31
    1/11/2 — 1/30
    共享 29 天    1/31
    移入

    今天退出 ≠ 今天才开始不用。
    今天留存 ≠ 今天支付。
    今天回流 ≠ 召回策略带来增量。

    理解这三个区别，才能把每日 MAU 变化接到正确的业务动作。

    01 / 07 · 买来的人，为什么没留在大盘里

    先定义一个能每天对账的增长问题

    买量持续带来新客，月末 MAU 却没怎么涨。原有月报分别记录拉新、留存与流失，但缺少一条能解释大盘变化的等式。

    我把分析对象统一为用户，把活跃统一为支付行为。这里每天更新的是过去 30 个自然日有支付的去重用户数，记为 MAU₃₀；它区别于自然月 MAU，也区别于登录活跃。

    原报表今天新增多少
    →
    需要补的问题同时有多少人退出活跃池
    →
    可用交付MAU₃₀ 的每日流入 / 流出

    先让新增和流失解释同一个支付用户池，才知道大盘停滞是进入少，还是退出多。

    02 / 07 · 把 30 天窗口只移动一天

    只改两端，才能解释今天的净变化

    自然月对比适合月报，但每天的增长诊断需要固定长度、每日滚动的窗口。把旧窗口 [t−30, t−1] 平移为新窗口 [t−29, t]，只换掉两端。

    旧窗口 · 1/30
    1/1
    移出    1/2 — 1/30
    共享 29 天    1/31
    新窗口 · 1/31
    1/11/2 — 1/30
    共享 29 天    1/31
    移入

    只要在共享的 29 天里支付过，用户就同时在两个集合里，今天属于 Retained。真正改变 MAU₃₀ 的人，只能从两端找到：今天进入的人，以及最早一天移出后再无支付的人。

    Overlap Window 的价值：把大盘的一天变化，精确对应到进入 / 退出活跃池的用户名单。它没有提前发现流失，退出仍有 30 天等待。

    03 / 07 · 哪一天退出，哪一天最后支付

    同一个用户，有两个不能混写的日期

    1 月 1 日最后一次支付
    →
    1 月 2–30 日没有支付
    仍在 1/30 的 30 天池内
    →
    1 月 31 日当天也未支付
    从 MAU₃₀ 退出
    支付轨迹举例1/31 状态为什么
    1/1 后一直未支付Churned旧窗有、新窗无；退出日 1/31，最后支付日 1/1。
    只在 1/10 支付，1/31 未支付Retained1/10 属于共享区间；留存不要求今天支付。
    1/31 首次支付New新窗有、旧窗无，全历史第一次支付就是今天。
    12/15 支付后停用，1/31 再支付Resurrected新窗有、旧窗无，但更早有支付历史。
    1/1 和 1/31 都支付Retained两个窗口各有支付，即使共享区间没有支付。

    1/31 是按 30 天规则确认退出的日期，1/1 是可回查的最后支付日期。1/1 当天可以支付多次，更早也可以支付过。由窗口关系无法知道用户真正决定离开的时刻或原因。

    回流是否证明召回有效？

    回流只说明用户在旧窗口没有支付、今天重新支付。可能来自发薪、自然需求或触达；要估计召回策略增量，需要同期对照或实验。

    同理，新进入者今天支付，不代表未来只有一天活跃。“瞬时脉冲”要等后续行为才能判断。按这个 30 天退出定义，回流用户 7 天后仍在窗口内；7 日未复购可以另算，但不能叫同口径的“7 日再流失”。

    精确的是最后支付日和退出记账日；原因需要再查。Retained 也只是两窗都在，不代表每天或今天活跃。

    04 / 07 · 四种状态怎样对上 MAU

    状态互斥，两个窗口都要能还原

    今天的存量MAU₃₀(t) = New + Retained + Resurrected
    昨天的存量MAU₃₀(t−1) = Retained + Churned
    今天净变化ΔMAU₃₀ = New + Resurrected − Churned

    Churned 已不在当前活跃池，因此不能把四项都加进今天 MAU。相邻窗口移动时，这四类互斥；连续两窗都不在的沉默用户不参与当天对账。

    一个五人例子，验证边界与对账
    用户支付记录1/31 状态
    A1/1退出
    B1/10留存
    C首次 1/31新增
    D12/15、1/31回流
    E1/1、1/31留存

    旧窗 A、B、E 共 3 人；新窗 B、C、D、E 共 4 人。New = 1、Resurrected = 1、Retained = 2、Churned = 1，所以 4 − 3 = 1 + 1 − 1。

    按渠道再拆时，用户要有唯一、稳定的归属。否则同一用户在两天间被重新归因，就可能制造某渠道的虚假流入 / 流出。

    恒等式既是业务解释，也是数据验收：对不上时先查去重、历史缺口、归因变化与日期边界。

    05 / 07 · SQL 怎样保住这两个边界

    先保留用户级变化，再聚合成看板

    底层先把支付明细去重为用户 × 支付日。每日输出一行用户状态，保留 anchor_date、first_pay_date、last_pay_date 与获客渠道，才能从大盘下钻回用户。

    可读 SQL：两窗 FULL OUTER JOIN
    -- :anchor_date 是当天；pay_user_day 已按 user_id × dt 去重。
WITH curr AS (
  SELECT DISTINCT user_id FROM pay_user_day
  WHERE dt BETWEEN DATE_SUB(:anchor_date, 29) AND :anchor_date
), prev AS (
  SELECT DISTINCT user_id FROM pay_user_day
  WHERE dt BETWEEN DATE_SUB(:anchor_date, 30)
               AND DATE_SUB(:anchor_date, 1)
)
SELECT :anchor_date AS anchor_date,
       COALESCE(c.user_id, p.user_id) AS user_id,
       CASE
         WHEN c.user_id IS NOT NULL AND p.user_id IS NOT NULL
           THEN 'Retained'
         WHEN c.user_id IS NULL THEN 'Churned'
         WHEN f.first_pay_date = :anchor_date THEN 'New'
         WHEN f.first_pay_date < :anchor_date THEN 'Resurrected'
         ELSE 'Unknown_history'
       END AS state
FROM curr c
FULL OUTER JOIN prev p ON c.user_id=p.user_id
LEFT JOIN first_pay_user f
  ON COALESCE(c.user_id,p.user_id)=f.user_id;

    first_pay_user 保存全历史首次支付；不能只在近 30 天里取 MIN，也不能以注册日代替首次支付。Unknown_history 单列并排查，不硬塞进 New。存在未知历史时，当前窗用 New + Retained + Resurrected + Unknown_history 对账；净变化用 New + Resurrected + Unknown_history − Churned 对账。未知清零后，再发布完整的四类生命周期拆分。

    大表如何少扫数据，又不漏掉退出？

    可维护每日用户最近支付日与首次支付日：今天有支付且上次支付早于 t−30（或从未支付）的人构成进入；截至今天最近支付日恰为 t−30 的人构成退出。上次支付等于 t−30 且今天又支付的人，两窗都在，仍是 Retained。

    每次支付可安排一个“30 天后到期”的候选；到期日核对是否有后续支付，有则取消旧候选。仅在支付事件上跑 LAG 会漏掉 Churned，因为退出当天通常没有事件。

    稳定的数据分区到齐后出数；迟到支付补进历史时，重算受影响的窗口和相邻状态，避免将数据延迟误报为退出。无事件只有在分区完整时才等于零支付。

    每一天先验收：用户状态唯一，当前与前窗计数都能还原；含 Unknown_history 在内的对账差额为 0。缺历史的人单列，不能从 MAU 净变化中漏掉。

    06 / 07 · 渠道退出多，就该停买量吗

    从“退出人数多”走到“哪批用户值得复查”

    看板下钻发现某些网盟渠道的新支付用户多，后续退出也偏高。这给渠道质量复查提供了名单，但退出人数本身会随获客规模增长。

    退出名单anchor_date = t
    last_pay_date = t−30
    →
    回接批次首次支付日
    固定获客渠道
    →
    同龄比较相同成熟时长
    再次支付 / 退出 / 贡献

    比较渠道时，用同一首次支付批次、同一观察时长，再看退出比例或后续支付贡献。不能用今天 Churned ÷ 今天 New；两边不是同一批人。也不能把新渠道尚未成熟的用户，与老渠道已经观察满 30 天的用户直接比较。

    如何定义一个真的可比的渠道指标？

    例如，对首次支付日在 d、已经观察到 d+30 的用户，计算“截至 d+30 未发生第二个支付日的人数 ÷ 该首次支付批次人数”。它对齐的是一次性支付后的流失风险；其他支付节奏可以用同一随访长度的复购率、支付频次或净贡献补充。

    渠道使用稳定获客归因；最后一次支付参与的活动另存一列。今天回流不改写原获客渠道，否则把营销触达与获客来源混成一个维度，渠道账会变。

    Overlap Window 告诉业务先查哪批人；同龄批次与成本、贡献比较，才支持预算调整。

    07 / 07 · 最后交付给业务什么

    把月末的一个数字，变成每天能追查的流转

    我将滚动窗口的用户状态接入增长看板，让新增、回流与退出能和 MAU₃₀ 的净变化对账，再从退出用户追到最后支付日、获客渠道与批次。

    交付层业务可以采取的动作
    每日总览看新增与回流是否被退出抵消；决定优先查进入还是退出。
    异常下钻回到具体退出用户，核查最后支付日期与渠道集中度。
    渠道复查优先复查新客多、后续退出偏高的网盟批次，再按同龄表现和贡献讨论预算。

    项目把“买量很多但增长不动”变成可定位的数据问题，为渠道预算复查和留存优化提供依据。要验证某次削减预算或召回策略的效果，仍应另设比较，不能从流转恒等式直接得到策略增量。

    核心成果：用只差一天的窗口，把每日净增长落到可追溯的用户变化；把看板异常交给具体的渠道与留存动作。
