# 用多 Agent 做一个 AI 反思产品：我的技术思考

<div class="insight-hero" markdown>

**一句话项目背景**：我把和 AI 深聊后真正有用的部分，压缩成一张“晶体卡”。它不保存几千字对话，只保存被触发时最需要的三件事：发生了什么、先抓住哪句话、接下来做哪个小动作。项目背景和使用场景我之前写在这篇文章里：[天天内耗的大学生，用 3 个 agent 给自己造了一个“改命工具”](https://www.superlinear.academy/c/share-your-projects/3-agent)。

**这篇文章想讲的不是项目故事，而是我做完以后对技术的理解**：一个原本只能靠人感觉判断的问题，怎样被拆成可路由、可装配上下文、可质检、可回滚的 AI 产品系统。

</div>

---

## 0. 先看最终形态：把长回答压成稳定结构

人在焦虑被触发的那一秒，读不进几千字安慰。他真正需要的不是完整对话，而是能让自己先停下来的短结构。

```html
<card>
  <what_happened>这不是预测未来，而是焦虑在用想象力制造痛苦。</what_happened>
  <first_sentence>害怕在心里，我在此刻。</first_sentence>
  <small_action>问：这个担心能不能导出一个具体动作？不能就标记为噪音。</small_action>
</card>
```

这个 HTML 例子不是为了炫技，而是为了说明项目的第一性原理：

> AI 产品不是把模型生成的长答案原封不动交给用户，而是把模糊的智能输出整理成稳定结构。

结构稳定以后，才谈得上检索、更新、评测和产品化。

---

## 1. 第一个思考：AI 产品 = 模型能力 × 上下文质量

应用层 AI 产品的主战场，通常不是训练模型，而是上下文工程。

白话讲：模型像一个能力很强但不了解你业务的人。你不只是问它“帮我做得更好”，而要决定它工作时应该看到什么、不应该看到什么、按什么顺序看、最后输出成什么结构。

<div class="principle-grid" markdown>

<div class="principle-card" markdown>

### 第一性原理

模型决定基础能力；上下文决定它能不能做好这道具体题。

</div>

<div class="principle-card" markdown>

### 我的实现

我没有 fine-tune。改进都发生在上下文：原始问题、历史候选、风格词典、结构约束、质检规则被拆开给不同角色看。

</div>

<div class="principle-card" markdown>

### 能力信号

真正的能力不是“会写 prompt”，而是知道上下文该怎么拆、谁该看什么、哪些材料应该被禁止注入。

</div>

</div>

我一开始犯过一个错：以为示例越多越好，于是把大量历史回答、风格反馈、好句坏句都塞给模型。结果输出反而越来越平均，既有一点安慰，又有一点分析，最后变成黏糊糊的 AI 腔。

后来我才意识到，长上下文不是越长越聪明。它更像开会：如果一个人同时听产品愿景、用户吐槽、历史代码、风格要求、质检规则、部署脚本，他不一定更清楚，反而可能分不清自己这一步到底该干什么。

所以我把工作台拆开。不是因为我喜欢复杂架构，而是因为每一步要解决的问题不同：

<div class="flow-strip" markdown>

<div class="flow-step" markdown>

**1. 问题分诊**

只看用户这次的问题和少量历史候选，判断这是新问题，还是旧问题的新补充。

</div>

<div class="flow-step" markdown>

**2. 写成短卡**

不看原始长对话，只看分诊结果和风格词典，把诊断翻成用户能用的短结构。

</div>

<div class="flow-step" markdown>

**3. 质检**

不看写作者 prompt，也不看原始对话，只看成品卡和规则，判断有没有破坏契约。

</div>

<div class="flow-step" markdown>

**4. 安全入库**

不调用模型，只由脚本把通过质检的结果写进文件。

</div>

</div>

这背后的产品判断是：**上下文不是资料仓库，而是工作台。工作台上只应该放这一步真正要用的工具。**

这也是我在面试或作品展示里更想传递的信号：我不是在堆 agent，而是在设计“信息如何进入模型”的系统。

## 2. 可视化：上下文到底是怎么被组装进模型的

“上下文工程”很容易听起来像一个大词，所以我专门做了一个交互式 HTML demo，用来展示同一条对话在不同阶段到底装进了哪些上下文块。

<div class="demo-embed" markdown>

<iframe src="../context-assembly-demo.html" title="上下文组装演示" loading="lazy"></iframe>

</div>

<a class="md-button" href="../context-assembly-demo.html">打开完整上下文组装演示 →</a>

这个 demo 展示的是我项目里最关键的 `build_context` 过程。每个 prompt 的 frontmatter 会声明自己需要哪些输入：

```yaml
inputs:
  - { name: question_md, type: markdown_file }
  - { name: route_helper_output, type: json }
  - { name: schema_excerpts, type: doc_section_set, sections: [...] }
  - { name: v3_fewshot, type: example_set }
```

然后 `build_context()` 按顺序把这些块拼成最终 user message：

```python
if typ == "markdown_file":
    blocks.append(read_file(path))
elif typ == "json":
    blocks.append(json.dumps(val))
elif typ == "doc_section_set":
    blocks.append(extract_doc_sections(source, sections))
elif typ == "doc_full":
    blocks.append(read_file(source))
elif typ == "example_set":
    blocks.append(format_examples(items))
```

这里真正有意思的不是代码，而是设计：

- `doc_section_set` 只抽文档中特定章节，避免把整份规则灌给模型。
- `doc_full` 只用于唯一权威文件，比如风格词典，因为那份文件必须完整。
- `example_set` 用少量高质量样本对齐风格，而不是把所有历史样本塞进去。
- `forbidden_inputs` 明确声明某个阶段不能读什么，防止上下文污染。

这就是我理解的上下文工程：**不是把资料塞满，而是让每个阶段只看到它该看的东西。**

## 3. 第二个思考：自然语言也要像软件一样有接口

很多人写 prompt 的方式像许愿：“请你深刻一点、自然一点、不要 AI 味、要有洞察。”

问题是，这种指令不可测试，也不可复用。它更像对浏览器说“请把网页做高级一点”，而不是写出明确的 HTML。

HTML 为什么稳定？因为它有结构：

```html
<h1>标题</h1>
<p>段落</p>
<button>按钮</button>
```

浏览器不需要猜“这里是不是标题”。结构已经告诉它了。

我在这个项目里做的事，本质上也是给自然语言任务设计接口。一个“好回答”太模糊，所以我把它拆成三个字段：

- **机制**：这次触发背后的因果结构是什么。
- **入口句**：触发当下先抓住哪一句话。
- **小动作**：5 分钟内身体真的能做什么。

这样一来，“写得好不好”至少有一部分变得可检查：

- 入口句是不是太长？
- 小动作是不是真的能执行？
- 机制有没有退化成空泛安慰？
- 新增内容是不是覆盖了旧内容？

这就是 Software 3.0 的一个朴素版本：当自然语言变成新的编程界面，软件工程原则没有消失，反而更重要了。你还是需要拆任务、定接口、做单元测试、处理异常。

## 4. 第三个思考：Router 不能让 LLM 自由发挥

LLM 很擅长读懂语义，但它不是稳定的规则引擎。尤其在分类、路由、选择下一步动作这种地方，它偶尔抖一下，后果会被后面的流程放大。

我的项目里有一个具体问题：一段新对话来了，它应该变成一张新卡，还是补充到旧卡下面？

如果交给 LLM 直接决定，它可能今天觉得是新卡，明天觉得是旧卡。单看一句输出差别不大，但对知识库来说，这是结构污染：该合并的东西散了，该分开的东西被揉在一起了。

所以我做了一个很轻的确定性路由器：

<div class="evidence-grid" markdown>

<div class="metric-card" markdown>

**先召回**

Python 从旧卡里检索最相近的 top-5，而不是让模型凭空回忆。

</div>

<div class="metric-card" markdown>

**再判断**

规则层给出初步建议和置信度，不确定时才让 LLM 做语义复核。

</div>

<div class="metric-card" markdown>

**最后设闸**

写入前仍然要过质检，不通过就进入人工 review。

</div>

</div>

这背后的技术判断是“确定性路由器”：**LLM 处理模糊语义，规则层处理稳定边界。**

这种边界意识可以迁移到任何业务 AI：LLM 读非结构化材料、提出假设；规则层处理明确计算和权限边界；高风险动作交给人或安全脚本确认。你不需要知道我的个人成长领域，也能看懂这个系统形状。

更具体一点，Router 的数据流是这样：

```text
用户对话.md
  │
  │  1. 剥掉 AI response，只保留用户真正问的话
  ▼
question_text
  │
  │  2. 和每张旧卡的 title + trigger + questions 做字符 trigram 匹配
  ▼
top-5 candidates + score
  │
  │  3. 显式阈值给 route_hint
  ▼
{ route_hint, confidence, candidates }
  │
  │  4. LLM 只在候选范围内复核语义
  ▼
最终 route：new / update / meta
```

这一步对我很重要。确定性路由器不是为了显得高级，而是因为 route 是一个小决策、大后果的开关：路由错了，后面的生成再漂亮，也是在错误的知识结构上加工。

## 5. 第四个思考：评测器不要贪心，只判能低成本验证的事

我一开始也想过：能不能让质检模型判断一张卡“是不是真的治愈用户”“机制是不是深刻”？

后来我放弃了。

因为这类判断太像人类品味，短期内很难低成本验证。一个心理机制到底有没有用，可能要看用户下次被触发时能不能想起来、想起来后能不能做动作、做完后有没有松动。这不是一次模型打分能解决的。

所以我把质检模型的职责收窄到可验证的部分：

<div class="principle-grid" markdown>

<div class="principle-card" markdown>

### 它不判什么

不判“人生道理是不是真的对”，不判“这段话有没有真正改变一个人”。

</div>

<div class="principle-card" markdown>

### 它判什么

字段是否完整、入口句是否过长、新增内容是否覆盖旧卡、有没有复制旧内容假装更新。

</div>

<div class="principle-card" markdown>

### 为什么

越容易验证的任务，越容易被 AI 稳定做好。这就是 Verifier's Law。

</div>

</div>

这句话对 AI 产品落地非常关键。

换成任何真实业务助手，第一版都不要急着证明“AI 真的懂业务”。可以先证明更具体的事：报告有没有漏掉核心指标；结论和数据有没有矛盾；建议动作有没有超出权限；有没有使用不合规表达；诊断是否能指出对应证据，而不是只给笼统建议。

**评测不是为了显得严谨，而是为了知道系统在哪些边界上可以被信任。**

## 6. 我不套通用 benchmark，因为我要测自己的决策边界

很多 AI 项目会说“效果不错”，但进入产品落地以后，这句话没用。你必须说清楚：哪里不错，怎么证明，错了代价是什么。

我给质检模型做了一个 20 条的 golden dataset。真实数据有个麻烦：我线上留下来的卡几乎都是好卡，因为坏卡当时没有入库。只有正样本，证明不了质检模型能不能拦住坏卡。

所以我做了一个工程补偿：拿真实好卡，人工注入一处明确违规，构造负样本。

<div class="metric-row" markdown>

<div class="metric-card" markdown>

**负样本来源**

真实卡 + 单点扰动，而不是凭空编坏例子。

</div>

<div class="metric-card" markdown>

**核心指标**

漏放率：该拦的坏卡有没有被拦住。

</div>

<div class="metric-card" markdown>

**真实发现**

同一输入重跑会 fail/pass 跳变，所以评测器自身稳定性也要测。

</div>

</div>

一次真实跑分里，9 条应该拦截的坏卡全部被拦下，漏放为 0；同时有 3 条误拦，属于把本来可以通过的卡送去人工 review。对质量闸门来说，这是可以接受的失败方向：宁可多看几张，也不要把坏卡放进库。

更有意思的是，我还观察到质检模型本身会抖。同一条输入，temperature 设 0，第一次 fail，重跑又 pass。

这让我意识到一个更深的评测点：**评测器本身也要被评测。**

如果一个商家诊断报告今天被判合格，明天同样输入又被判违规，产品经理就不能只看 accuracy，还要看稳定性。边界样本要跑多次，看 flip rate；必要时用多数投票，或者直接送人工。

## 7. AI 只建议，真正写库的是脚本

LLM 的创造力是优点，也是风险。它会补全、联想、改写，有时还会自信地做出你没授权的事。

所以我的项目里，模型不会直接改知识库。

模型做三类事：提出诊断、写出候选卡片、给出质检 verdict。真正入库的是 Python 脚本，而且只有质检结果是 pass 才自动写入。不是 pass，就进入人工 review。还有一个 `--no-push` 模式，可以跑完整条链路但不碰真实数据。

这里我的理解是“AI 建议，人或安全脚本执行”。关键不是有没有自动化，而是自动化发生在哪一层。

在任何有真实后果的产品里，这个边界都很重要。AI 可以提出建议，但真正改变用户资产、权限、评级、预算或知识库状态的动作，都应该经过规则层和人工确认。

## 8. 记忆不是覆盖，而是保留演化轨迹

这个项目里还有一个看似小、但很关键的产品设计：旧卡不被覆盖，新理解只追加。

一开始我自然地以为，更新就是把旧字段改掉。后来 dogfood 后发现不对。晶体卡不是普通数据库记录，它记录的是一个人在某个时间点理解自己的方式。旧机制、旧入口句、旧小动作不是“过时字段”，而是历史资产。

所以现在更新逻辑是：原卡保留，新洞察挂在更新历史里，用户可以看到这个问题是怎么一层层长出来的。

这和很多业务系统也有关。任何长期跟踪对象，不管是用户、商家、项目还是知识库，都不应该只保留“最新状态”。更好的做法是保留每次诊断、每次动作、每次结果回填。

只看当前状态，你只能问“现在怎么样”。保留演化轨迹，你才能问“哪个动作真的带来了变化”。

## 9. 这件事对应的 AI 产品能力

<div class="principle-grid" markdown>

<div class="principle-card" markdown>

### 拆业务指标和流程

不要笼统说“用 AI 提升效率”，而要拆到问题识别、候选召回、诊断生成、合规质检、动作建议、效果回填。

</div>

<div class="principle-card" markdown>

### 判断 LLM 边界

语义材料交给 LLM，确定规则交给代码，高风险动作留给人。

</div>

<div class="principle-card" markdown>

### 设计评测

先做任务对齐的离线评测和人工校准，再看线上代理指标，最后才谈业务指标。

</div>

<div class="principle-card" markdown>

### 做上下文工程

用户画像、历史记录、规则文档、候选样本、评价标准和禁止输入，要按任务分层装配。

</div>

</div>

所以这个项目虽然从一个很私人的问题开始，但它训练的是一个很通用的 AI 产品能力：

<div class="quote-panel" markdown>

把模糊的人类判断，拆成有边界、有证据、有评测、有回滚的系统。

</div>

这就是我真正想展示的 technical insight。不是“我会用 agent”，而是我知道 agent 在产品系统里应该站在哪、不能碰哪、错了怎么发现、怎么把人的判断重新接回系统。
